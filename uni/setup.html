Focus timer

The timer is available on all authenticated Taskitator pages. Its account-scoped local record stores absolute cycle deadlines, duration/session settings and sound/vibration/screen-awake preferences. Navigating or reloading restores the same countdown; suspended pages catch up against elapsed time. Open tabs use browser locks where supported to serialize transitions. No timer ticks or screen preference changes push personal task data to the server.

Choose study/break duration and sessions, then Start new sessions. Pause/resume and Reset are explicit controls. Sound and vibration are independently toggled. Study end uses two pulses, break end three short pulses, and full completion a longer three-part pattern. Delayed restoration shows the current cycle rather than replaying a backlog of old alarms. Sound may need a tap after navigation; browser suspension may delay alerts. Vibration is feature-detected and is unavailable in some browsers.

Keep screen awake requests a screen Wake Lock while the timer is running and the page is visible. Pause, hiding the page or leaving releases the request; returning attempts to reacquire it. The browser/OS can deny or release it. The UI indicates requested versus active state.

The page shows a floating timer tag. Browsers supporting Document Picture-in-Picture also offer a Floating timer button, opening a read-only display with no Pomodoro controls. It can stay above other windows while the originating tab remains open. Closing that tab closes the floating window; a web app cannot maintain a system overlay afterward. The stored countdown still restores when Taskitator is reopened. No native-phone overlay or background alarm is promised.

Task editing and subtasks

Editing now uses a separate task/recurrence draft. Adding quick subtasks, changing recurrence, adding tags, removing a reference, or changing saved criteria within that draft does not save the task or schedule a push. Press Save to commit. Cancel, Escape or navigating away with changes asks “Changes unsaved. Discard your changes?” Browser tab closure uses the browser’s standard unsaved-changes dialog. Another task or a new child editor also requires handling the current draft. A new draft subtask must be saved before opening its own editor.

Save merges changed tasks into the latest local task list; conflicting external changes or a changed account prevent overwriting. References are saved/deleted only during explicit Save. Delete in the edit panel marks the branch for deletion and requires Save; existing protected-task and Emergency Bypass rules still apply.

Recurrence controls now appear above Quick Subtasks in creation and editing. Quick Subtasks are the last content section before action buttons. Enter commits a quick subtask directly and retains focus; mobile line-break and implicit-submit paths are handled as well. Consecutive numbering is disabled until active Pro has been confirmed, and is disabled again when status becomes inactive. Existing server-side Pro checks remain in place.

Local tree display and Copilot name

Collapsing/expanding a task tree changes only the local collapsed-node record and redraws the tree. It never calls the task-save/push path. The tablet floating Copilot label, title and accessible name now use the configured Copilot name, refreshed after settings changes and synchronization.

Before applying a patch

  1. Start with the hardened root-layout consolidated project. Apply phase 1, then phase 2, and later patches in order. Each patch contains only its created or modified files; keep the rest of the repository.
  2. New Universe files belong in uni/. Existing root files stay at root. Preserve image/, icon/, SYSTEM_PROMPT.md and the existing workflow path. Do not run the old consolidation cleanup script.
  3. Use Node 22.13 or newer (Node 24 is recommended). Keep your existing Clerk, Keyo, encrypted API vault, personal coordinator, and production settings. Do not paste secrets into HTML or commit them to GitHub.
  4. Use separate development D1, R2 and Worker resources. A binding name in configuration does not prove the resource is deployed. The included universe_dev D1 ID is a placeholder for local development, not a production resource.
  5. Before a remote migration, confirm the target database ID, make a backup, and rehearse on a separate development database. Never delete personal data as an upgrade step.

Using projects, tasks and reviews

  1. Open Universe, select a group, and create a project as owner/admin. Create a human-reviewed task with criteria, selected assignees, reviewer roles, optional UTC opening/due dates and optional late submissions.
  2. Everyone’s creates one assignment per selected member. Shared creates one assignment that any selected current member may submit. Joining later adds no past assignments.
  3. Submit proof text and/or up to three files: PNG, JPEG, PDF or plain text; 5 MiB maximum per file. Files use authenticated JSON uploads, SHA-256 checks and private R2 objects. A staged upload expires after one hour unless attached. Upload bytes alone never complete a submission.
  4. Reference uploads require owner/admin. Adding a reference or editing criteria/assignees increments the task revision and resets affected assignments; previous decisions remain history. Editing creates fresh assignments and cancels the previous set. Old references are retained temporarily but are not current revision references.
  5. A selected reviewer role may approve/reject a pending submission with a reason. Self-review is prohibited. Concurrent decisions produce one committed result. A permitted reviewer can reopen a decided non-AI assignment with a recorded reason. Members cannot erase audited completion.
  6. Proof is readable by its submitter and current permitted reviewer roles only. Other group members cannot download another member’s proof. References are readable by current group members. All downloads are authenticated; names are text and bytes download as attachments.
  7. Proof text/files are retained for 30 days after a final decision, extended while disputed. Submitter or reviewer may open a dispute during retention; a permitted reviewer closes it, starting a fresh 30-day retention window. Pending proof is retained until a decision. Departure removes the departing account’s access immediately. Deletion fences access before hourly cleanup removes private objects; abandoned uploads also use recoverable cleanup.

Task and review flow

  1. Create/edit a task and choose Require Universe AI review; optionally require a human decision afterward. Human-only tasks continue without AI or credits.
  2. Submit proof first. The submitter requests a quote. Everyone’s allows saved Gemini key, or account Universe hosted credits for active Pro. Shared always uses hosted group credits, including when its submitter is Free.
  3. Quotes count the actual text/image/PDF input, enforce a 20,000-token input cap with counting headroom, bind the proof/criteria/model/key versions and expire after five minutes or at the next Riyadh day. Quote creation does not run inference or reserve credits.
  4. The submitter explicitly approves the displayed maximum. Hosted approval atomically reserves account/group daily and monthly credits and the global provider-spend ceiling. The maximum covers 20,000 input tokens and 1,024 total output tokens. References double credit usage; there is no batch review or batch discount.
  5. Completed responses settle actual reported input/output usage (including thought tokens), return unused holds and charge rejected proof too. Cost is integer nanodollars; credits are integer thousandths, using the existing 1,500,000-nanodollar credit value. Missing usage or invalid completed output consumes the accepted maximum; invalid output never approves completion. Actual provider spend is recorded independently from the user’s accepted credit maximum.
  6. AI approval alone completes an AI-only task. Combined tasks remain pending for a permitted human reviewer. AI rejection reopens the submission path through rejected status. Members cannot inject an approval or use personal completion grants to finish group work.
  7. Repeated approval/status requests reuse the same durable review. A timeout, process interruption, lost reply or expired lease never automatically purchases a second inference for that submission. Unknown outcomes retain the maximum hold. Review status is refreshed manually.
  8. Membership removal, account/group deletion, criteria edits or reassignment during inference prevent completion. Provider usage is still settled. AI-approved Shared work may be reopened only by a different owner/admin strictly above the completing actor’s recorded rank.

Recovery and operational gates

A durable provider result is saved before settlement. The existing cleanup alarm completes interrupted settlement without sending another inference. Never clear running/uncertain reviews merely because they are old: first reconcile the request with provider usage as an operator, preserve its receipt and account for any spend. Uncertain reviews deliberately remain held; this patch does not pretend the provider can report whether an ambiguous request ran.

If reported usage exceeds reserved token bounds, the global universe_ai_safety row blocks further hosted approvals. Reconcile usage, adjust verified rates/limits/configuration and re-run the pilot before an operator clears that block. Review records contain accounting/decision metadata, not raw activation keys, API keys or proof file bytes.
