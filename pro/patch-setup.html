Taskitator patch installation

Built against Taskitator-main-8.zip. The ZIP contains only modified and created files at their repository paths. Every new file is inside pro/. The blocker guide and macro are excluded.

Install and deploy both parts

  1. Back up your repository, then extract this patch at its root, merging folders and replacing the matching files. Do not replace the full repository with this patch.
  2. From the complete updated repository run npm test. Tests also need the new pro/audit-policy.test.js file. Keep all existing application files, tests, configuration and images.
  3. Publish the changed website files through your existing website deployment. Include the changed pro/pro-client.js, pro/pro-ui.js, pro/profile-ui.js, style.css, page files, and both sw.js and auth-bootstrap.js. Their cache version must match.
  4. Redeploy the existing Worker from the complete repository with npm run deploy:worker, using existing Cloudflare credentials. Alternatively run your existing security Worker deployment workflow if installed. The configured entry point is cloudflare/worker.js, resolved from cloudflare/wrangler.toml. It imports pro/pro-backend.js and the new pro/audit-service.js/pro/audit-policy.js. Copying a standalone root worker.js cannot install this patch.
  5. Keep current bindings, storage, encryption keys, Clerk settings and licensing configuration. No D1 migration, new Durable Object or destructive reset is required. Do not rename the shared taskitator-v1 Durable Object: it coordinates username claims and hosted credit reservations.
  6. Purge cached website HTML/CSS/JavaScript in Cloudflare after publication, then reopen Taskitator. The service worker activates the new cache before loading account data. Unsynced drafts and logout handling are preserved.

Username uniqueness

Names are now claimed through the existing Worker registry in a storage transaction. Mazen, mazen and MAZEN are the same claim. Display casing is retained. Names use 3–20 ASCII letters, numbers or underscores. Reserved names remain unavailable. A rename releases an old claim only if the same account owns it.

No Clerk username option needs enabling. The Taskitator editor no longer writes mutable Clerk metadata. Previously duplicated metadata names are not automatically promoted into unique claims: users without an existing valid registry claim will see Set username and must choose an available name. A valid existing registry claim is retained.

Taskitator usernames are public display names, not alternate login credentials. The broken custom lookup that returned an account's private email is disabled. Use Clerk email/password or Google sign-in. The login page now separates sign-in/create-account choices, opening a workspace, and the optional one-time import of an older Taskitator account. Recovery copies and sync conflict gates remain in place.

Hosted AI settings and accounting

Set the existing Worker secret CLAUDE_API_KEY (or its supported alias ANTHROPIC_API_KEY) to an Anthropic API key with access to claude-haiku-5-5 and the token-counting endpoint. Keep it out of browser code and source control. There is no automatic fallback to a more expensive hosted model.

PolicyBehavior
Credit balances45 daily and 1,000 monthly, including previously activated subscribers. Existing usage is retained. Both periods use Asia/Riyadh; the monthly period starts on the first day.
Dynamic credits1 credit represents $0.0015 of hosted provider cost. Fractional credits are rounded up to 0.001. A normal audit uses ×1; an audit that includes a reference exemplar uses ×2. Exemplars are actually included in the provider request.
Batch discountTwo or more tasks receive 25% off each task. The single combined request sends shared proof once; its actual provider cost is divided equally across tasks, then each task's exemplar multiplier and discount are applied. Charges are added together. A one-task batch has no discount. There is no flat-one charge or ten-credit cap.
PricingThe fixed Haiku 5.5 rates used by this patch are $0.10 per million input tokens and $0.50 per million output tokens, checked October 21, 2026. Example: 1,000 input + 200 output tokens cost $0.0002, or 0.134 normal credits / 0.267 exemplar credits. Two ordinary batch tasks sharing that total cost are charged 0.050 credits each.
Large uploadsAt most five proof files, 5 MiB per proof/exemplar and 20 MiB combined. The complete prompt, proof files, PDF content, criteria and all exemplars are sent to the provider's free token counter before paid inference. The count plus 20% headroom must fit within 20,000 input tokens for the entire request. A file's declared page count or dimensions cannot bypass this check. Split large PDFs or use fewer tasks if rejected.
Output and previewOutput is capped at 1,024 tokens for a single audit and 384 per batch task, up to 4,096. The preview shows an estimate and maximum reservation, including per-task charges. The reservation covers the full 20,000 input-token safety envelope plus maximum output. It may exceed the estimate; unused credits are released after settlement. A smaller remaining balance may be insufficient for a worst-case reservation.
Monthly provider allowanceNew requests atomically reserve against a $2 monthly hosted-provider spending allowance per account, separately from customer credits. Successful responses settle actual usage, including rejected proof. Provider failures refund customer credits; billable malformed responses still count toward provider spend. Lost/unknown outcomes conservatively retain their provider spend reservation. No inference is automatically retried.
Retries and failure recoveryOperations are tied to the account, session, full input hash, action and policy. Repeated submissions return the saved result or a pending error rather than purchasing another audit. A lost browser response reuses the same operation on retry within that page. Quote-only cancellation starts no paid review. A Worker crash after reservation leaves a pending operation reserved; an operator must reconcile it against provider usage before releasing it. Do not blindly clear pending or uncertain reservations.

Provider token counts are estimates, so the patch uses headroom and conservative reservations. If reported actual usage ever exceeds a reservation, the full provider cost is recorded; the customer's approved maximum is retained, with overage absorbed by the operator. The $2 limit blocks subsequent requests based on recorded costs and outstanding reservations. It cannot retroactively prevent an unexpected provider overage or a provider price change. Configure an Anthropic project/organization spending limit as an additional overall safeguard and review rates before deployment.

Historical flat-credit records did not store provider token usage. Until a new monthly ledger exists, the patch carries old monthly credits at $0.0015 each as an estimate; exact earlier provider spending cannot be reconstructed from the uploaded project. Reconcile the current month with provider billing if strict historical accounting is needed. New operation records store hashes, billing and audit results; proof/exemplar bytes are not persisted by this billing code. Account deletion removes these new records and username claims without affecting another account's records.

References: Anthropic pricing, Anthropic token counting. These controls apply to hosted proof audits; your existing personal-key provider flows and licensing logic are retained.

If the published page still shows [email protected], purge its Cloudflare cache and ensure any HTML minifier preserves the exemption comments.
