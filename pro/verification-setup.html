Taskitator verification fix

Patch for the supplied Taskitator-main-7(2).zip baseline. Replace files at their existing repository paths, deploy the website, and redeploy the existing Worker. No live Clerk or Google account, deployed Worker, or real browser was used to validate this patch.

1. Replace these files

Repository pathChange
cloudflare/verification.jsChecks Clerk's backend reverification object, account/session, completed first-factor or multi-factor level, and millisecond timestamps against the current attempt. Removes Google approval without OAuth configuration. Uses version 2 grants and rejects older records.
cloudflare/vault.jsImports the grant version and checks it in the transaction that consumes key approvals. This additional two-line change is necessary because reveal/delete consume grants directly without calling the shared verification getter. It closes the old-grant bypass at those endpoints.
vault-client.jsAlways redirects Google confirmation to a validated Google OAuth URL. Preserves pending action/provider/session and callback recovery.
deletion-client.jsValidates Google's authorization URL and shows a setup/retry message on failure, releasing the busy state. Deletion still needs separate manual confirmation.
tests/security.test.js
tests/client.test.js		Uses the Backend API response format and adds verification, replay, scope, failure, URL and password-privacy regressions. Repairs the existing client DOM mock's missing style property.
pro/verification-setup.htmlThis setup page, the only new application-repository file.

Extract the patch at the repository root; do not create another Taskitator-main folder. Retain every other repository file. Both Worker files above must be deployed together. Existing grants, including pending confirmations, are deliberately invalid after this deployment; start a fresh confirmation.

2. Check Clerk password confirmation

  1. Open the Clerk production instance used by this website. Under Sessions → Customize session token, preserve existing custom claims and add:
    {"taskitator_reverification_id":"{{session.reverification_id}}"}
  2. Keep the standard fva claim. After a new password reverification, a fresh signed session token must contain a new nonempty taskitator_reverification_id and a nonnegative first-factor age of at most two minutes. Inspect locally; do not share bearer tokens or passwords.
  3. Keep CLERK_SECRET_KEY, CLERK_JWT_KEY, and CLERK_ISSUER configured on the same Worker and for the same Clerk instance. The issuer must match session tokens; the JWT key is Clerk's PEM public key. Keep ALLOWED_ORIGINS set to https://taskitator.mazendev.com unless your deployment intentionally uses another allowed origin.
  4. Use a password-enabled account to test the password option. Password entry and verification stay in ClerkJS. Taskitator receives only a signed session token and the action proof ID. The backend response does not expose the browser SDK's password strategy; the Worker validates completed first-factor evidence.

The Worker rejects baseline/reused IDs, wrong accounts/sessions, incomplete responses, expired attempts, and timestamps before the attempt or in the future. A grant lasts five minutes and authorizes one action. Clerk and Worker clocks must agree; retry a new confirmation if timestamp validation fails. Missing claims fail closed.

Reference: Clerk: action-specific reverification and signed claims; Clerk's Backend API schema (Reverification).

3. Configure real Google OAuth confirmation

In Google Cloud → Google Auth Platform → Clients, open the web OAuth client for Taskitator. Add this exact authorized redirect URI:

https://taskitator-sync.spacexmzez.workers.dev/auth/verification/google/callback

This matches the Worker base URL in auth-config.js, Worker name taskitator-sync in cloudflare/wrangler.toml, the existing PHASE-1-SETUP.txt instructions, and the callback route in cloudflare/worker.js. The account subdomain comes from auth-config.js; it is not specified by wrangler.toml. The deployed Cloudflare settings were not inspected.

Keep Clerk's existing Google login callback registered as well. Copy its exact value from Clerk's Google connection settings; do not replace it with this Worker callback. These callbacks serve separate flows.

On Cloudflare → Workers & Pages → taskitator-sync → Settings → Variables and Secrets, set:

SettingValue/type
GOOGLE_OAUTH_CLIENT_IDThe Google web OAuth client ID, Text.
GOOGLE_OAUTH_CLIENT_SECRETThat same client's Google client secret, Secret. Never put it in browser files or GitHub.
GOOGLE_VERIFICATION_REDIRECT_URIText: the exact HTTPS Worker callback above, with no trailing slash, query or fragment.

Save/deploy the settings. Confirm your Google consent configuration permits your test account if the OAuth app is in testing. The Google identity must already be linked and verified in Clerk. All three Worker settings are required; missing or partial settings now produce a setup error and never approve the action. Google determines whether its existing session suffices or credentials are needed; an existing Taskitator session or linked Google identity cannot approve the action.

If your Worker intentionally uses a custom domain, register its exact callback with Google and use that same URI in the Worker setting. Do not change website or Worker addresses solely to install this patch.

4. Deploy the website and Worker

  1. Commit/upload the patched files to the existing repository and deploy through your normal website publishing process. Confirm vault-client.js, deletion-client.js, and this page are published. The existing service worker fetches both client scripts from the network; reopen or reload Settings after publication.
  2. Redeploy the Worker through GitHub Actions → Deploy Taskitator security Worker → Run workflow. The attached workflow is manual; pushing files alone does not trigger it. It runs npm test before deployment. Preserve its existing Cloudflare repository secrets and bindings.
  3. Alternatively, from the complete updated repository with Cloudflare credentials configured, run npm run deploy:worker. This deploys using cloudflare/wrangler.toml; no standalone Worker text file is needed. Run tests first.
  4. Keep existing vault encryption settings intact. Account deletion also requires the existing ACCOUNT_DELETION_ENABLED=true and deletion-storage setup from PHASE-1-SETUP.txt. Do not regenerate keys, recreate storage, or alter other feature settings for this patch.

5. Automated results and remaining live checks

Full configured suite: 91 passed, 0 failed, 0 skipped with Node 24.19.0 and a runtime compatibility adjustment for the unchanged Pro test's assignment to the getter-only globalThis.crypto. The actual test command was:

NODE_OPTIONS='--import=data:text/javascript,Object.defineProperty(globalThis,%22crypto%22,%7Bvalue:globalThis.crypto,writable:true,configurable:true%7D)' npm test

This adjustment makes the existing Web Crypto global writable in test processes; it does not replace Web Crypto, skip tests, or change deployed code. Plain npm test on this Node 24 runtime fails to load the existing pro/pro.test.js because of that pre-existing assignment. The repository's workflow selects Node 22; it was not executed here. If your runner reports the same TypeError, rerun the tests with the command above or use a compatible test runtime before deploying. No unrelated Pro implementation or test file was changed.

The suite uses signed local JWTs and mocked Clerk/Google HTTP, storage, and DOM objects. It covers fresh and invalid password proof responses, expiration/reuse, missing Google settings, old grants at consumption endpoints, unsafe redirect URLs, password failures and privacy, Google token validation, one-use callbacks and account/session/action/provider scope, and callback recovery without automatic deletion.
